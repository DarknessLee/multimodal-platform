> 依据材料：

> 本文是后续所有阶段开发的**总纲**；每阶段完成后同步更新本文状态、`docs/00`、`docs/01`、`docs/02`、`docs/04` 与 `README.md`。

## 0. 结论摘要

- 架构方案是**平台目标态**，包含 13 个微服务、3 类中台、10+ 外部系统、区块链/IoT/大数据等；直接照搬会超出演示范围且大部分能力无法验证。
- 当前 Demo 是**单车、单线路、单结算**的 v0 竖切：业务闭环成立，但只覆盖「下单→调度→三段运输→签收→账单」。
- v1 的定位：**单 Web 端、全 Mock、业务闭环优先**。用**模块化单体**模拟微服务，用**适配器 + 报文标准**模拟外部系统，用**进程内事件总线 + outbox** 模拟 MQ，用**哈希链 + 签章记录**模拟区块链存证，用**SQL 视图/看板服务**模拟数据中台。
- 按 **5 个阶段**递进，每阶段都保留可点通的全流程演示并扩展业务闭环；Stage 1 是主数据 + 受理闭环，之后依次补一单制/箱管、调度与可视化、结算与金融、集成与运营。

## 2. 当前 Demo 已具备（基线盘点）

- **业务闭环**：货主下单 → MTO 调度 → 承运人接单/提货/送达 → 港站进场/到港/到站 → 货主签收 → 结算出账 → 分段账单。
- **多角色**：货主 / MTO / 公路承运人 / 港站 / 结算（5 角色，单 Web 端角色切换）。
- **数据**：7 表（user、orders、container、waybill、waybill_segment、track_point、bill），MySQL 8。
- **接口**：10 个，统一 `/api`，JWT + 角色权限 + 状态机 + 事务。
- **Mock**：3 家公路承运商报价、固定海运/铁路段、线路经纬度、GPS 插值、95306/港口 EDI 文案。
- **演示**：2 条命令、5 账号、ECharts 轨迹/账单、accept 34 项断言、E2E 6 阶段 + 10 张截图、build 零错误。
- **不足**：单一路线模板、无主数据、无报价/合同、无一单制、无箱管、无运力池、无对账/发票/支付、无异常与预警、无集成日志、角色仅 5 个。

## 4. 演进原则（在 Mock 前提下贴近真实业务）

1. **业务闭环优先**：每阶段必须有一票订单从「受理」走到「结算」的可点通路径；不追求功能清单全量。
2. **Mock 真实感**：编码、报文、单据、金额、时效、箱型参数、港口/站点、企业名称均按真实业务规则生成；同一实体跨页面/跨阶段数据一致。
3. **标准先行**：先定数据字典、编码规则、状态机、报文中字段，再写代码；Mock 报文严格按标准结构输出。
4. **单仓单进程**：不引入 K8s、MQ、ES、时序库、真链、真地图瓦片；用模块/视图/进程内组件模拟，文档写清映射。
5. **接口兼容**：v0 的 10 个接口与演示路径不回退；新增能力以新接口 + 新页面增量交付。
6. **验收驱动**：每阶段更新 `docs/01` 演示脚本、`scripts/accept.mjs`、`scripts/e2e-smoke.mjs`；每阶段 `build` 零错误 + accept/e2e 全绿。
7. **文档同步**：阶段完成即更新 `docs/00`（范围/状态）、`docs/01`（演示/验收）、`docs/02`（接口契约）、`docs/03`（本文阶段状态）、`docs/04`（阶段接口契约）、`README`。

## 6. Mock 数据规范（真实业务标准）

### 6.1 编码与主数据规则

| 对象 | 规则 | 示例 |
|---|---|---|
| 集装箱号 | ISO 6346：4 位箱主代码 + 6 位序列 + 1 位校验位（含校验算法） | `MSCU7000001`（校验位按算法生成） |
| 港口/站点 | 港口用 UN/LOCODE；铁路货场用车站电报码（演示用 5 位） | `CNSHA` 上海港 / `CNWUH` 武汉港 / 吴家山 `21001` |
| 国家/地区 | GB/T 2260 行政区划代码 | 上海嘉定 `310114`、成都青白江 `510113` |
| 企业 | 统一社会信用代码 18 位（按 GB 32100 校验位算法生成） | `91310114MA1GXXXX0X` |
| 订单 | `MO + yyyyMMdd + 5 位序号` | `MO202610220001` |
| 委托 | `WT + yyyyMMdd + 5 位` | `WT202610220001` |
| 报价 | `BJ + yyyyMMdd + 5 位` | `BJ202610220001` |
| 合同 | `HT + yyyyMM + 4 位` | `HT2026100001` |
| 主运单（一单制） | `WB + yyyyMMdd + 5 位` | `WB202610220001` |
| 分段运单 | `SW + 运单序号 + 段序` | `SW202610220001-01` |
| 账单/对账单/发票/支付 | `BL / DZ / FP / PAY + yyyyMMdd + 序号` | `BL202610220001` |

### 6.3 关键报文（Mock 输出，结构遵循标准）

- **铁路需求车提报**（JT/T 1351-2020 语义）：`<RailDemandApply>` 含托运人、发站/到站电报码、箱型箱量、货物名称、需求日期、车种、报文流水号。

## 7. 分阶段路线图

> 每阶段结束均为**可演示的闭环**，并回归 v0 的 accept/e2e。

### Stage 1（✅ 已完成 2026-10-22）：平台基座与受理闭环
- **完成证据**：`docs/06-Stage1-验收报告.md`（build 零错误、accept 53/53、e2e 13 阶段/16 截图、v0 回归 34/34、冷启动通过）。
- **目标**：从「单车单线」升级为「平台受理」：主数据、客户/伙伴、线路、价格、报价、合同、订单中心 v1、角色扩展、审计与集成消息、总览看板。
- **新增/变更表**：customer、partner、contact、port_station、route_template、goods_catalog、container_type、price_rule、contract、quote、order（扩展）、order_cargo、integration_message、audit_log、notification、dict_data、role/permission（RBAC）、event_outbox。
- **核心接口**：认证与 RBAC、主数据查询/维护、报价（询价→报价→接受）、合同签署、订单 v1（多货物/合同/报价）、取消、总览 KPI、审计/集成消息查询。
- **页面**：平台总览、客户管理、伙伴管理、主数据（线路/港站/货物/箱型/价格）、报价工作台、合同管理、订单中心 v1、集成消息、审计日志。
- **演示闭环**：货主询价 → MTO 报价 → 货主接受生成订单 → 签署合同（Mock 签章）→ 调度 → 履约 → 签收 → 账单；看板与审计可见全过程。
- **验收**：build 零错误；accept v2 ≥ 50 断言；e2e v2 全流程；v0 履约链路不回退。

### Stage 2（✅ 已完成 2026-10-22）：一单制运单中心 + 箱管中心 + 单证与存证
- **完成证据**：`docs/09-Stage2-验收报告.md`（build 零错误、accept:stage2 33/33、e2e:stage2 6 阶段/6 截图、Stage1 53/53 与 v0 34/34 回归通过、33 表/312 条存证链校验通过）。
- 主运单/分段运单/交接事件链/单证（委托书、运单、装箱单、回单）、电子签章、哈希链存证。
- 箱管：放箱/提箱/进场/装箱/卸箱/还箱/箱损/堆存；箱号 ISO 6346 校验。

- **闭环**：一次委托生成一单制运单 → 放箱 → 提箱 → 分段履约 → 回单上传 → 签收 → 存证可查。

### Stage 3：调度中心与全程可视化
- 运力池（车辆/班列/班轮）、智能方案推荐（成本/时效/可靠度）、人工调整、中转衔接窗口、调度看板（GIS 简化）。
- 可视化大屏、节点跟踪、异常预警（延误/偏航/温湿度）、IoT Mock 读数。
- **闭环**：下单 → 方案推荐 → 调度确认 → 全程可视 → 异常处置 → 到达签收。

### Stage 4：结算中心 v2 与经营分析
- 计费引擎（价格规则 + 附加费 + 阶梯）、应收/应付、对账（承运人确认/差异工单）、电子发票、支付/保理 Mock。
- 数据中台 Mock：ODS→DWD→DWS→ADS 视图与经营指标看板。
- **闭环**：签收 → 自动计费 → 对账 → 开票 → 支付 → 结算完成，财务看板可查。

### Stage 5：集成中心与运营保障
- 集成网关（鉴权/限流/重试/告警/报文日志）、国家物流平台上报、银行/税务/CA/电子合同/ERP/WMS Mock、监管视角。
- 运营后台：数据字典、编码规则、系统配置、任务调度（Mock）、审计与数据质量。
- **闭环**：全链路演示脚本 + 全角色视角 + 集成报文可追溯 + 监管/经营看板。

## 8. Stage 1 详细设计

### 8.1 范围与不做

- 做：主数据、客户/伙伴、线路、价格规则、报价、合同、订单 v1（多货物/多箱型/收发货人）、RBAC 10 角色、审计、集成消息框架（先落 95306/港口/银行三类 Mock 报文日志）、总览看板。
- 不做（后续阶段）：一单制运单、箱管、调度算法、可视化大屏、对账/发票/支付、真外部对接。

### 8.2 数据模型（新增/变更，详见 `api/db/schema.sql`）

- `user` 扩展：customerId/partnerId、phone、email、status、lastLoginAt；角色扩展为 10 类。
- 新增：`customer`、`partner`、`contact`、`port_station`、`route_template`、`goods_catalog`、`container_type`、`price_rule`、`contract`、`quote`、`quote_item`、`order_cargo`、`dict_data`、`audit_log`、`integration_message`、`notification`、`event_outbox`、`permission`/`role_permission`。
- `orders` 扩展：orderType、customerId、consigneeId、contractId、quoteId、routeTemplateId、priority、totalAmount、currency、status 扩展（INQUIRY/QUOTED/CONTRACTED/PLANNED/…）。
- 保持 v0 表与接口兼容（waybill/segment/track/bill 不改结构）。

### 8.3 接口（详见 `docs/04-Stage1-接口契约.md`）

- 认证：`POST /auth/login`、`GET /auth/me`、`GET /auth/permissions`。
- 主数据：`GET/POST /customers`、`/partners`、`/ports`、`/routes`、`/goods`、`/container-types`、`/price-rules`、`GET /dicts`。
- 报价：`POST /quotes`、`GET /quotes`、`GET /quotes/:id`、`POST /quotes/:id/accept`。
- 合同：`GET/POST /contracts`、`POST /contracts/:id/sign`。
- 订单：`POST /orders`（v1）、`GET /orders`、`GET /orders/:id`、`POST /orders/:id/cancel`。
- 看板：`GET /dashboard/summary`。
- 集成/审计：`GET /integration/messages`、`GET /integration/systems`、`GET /audit/logs`、`GET /notifications`。
- 保留 v0：dispatch/segments/waybills/bills。

### 8.4 页面与角色

- 新增：平台总览、客户管理、伙伴管理、主数据（线路/港站/货物/箱型/价格规则）、报价工作台、合同管理、订单中心 v1、集成消息、审计日志。
- 角色菜单按权限矩阵渲染；保留 v0 履约页面（调度/任务/港站/跟踪/结算/账单）。
- 订单 v1 新建：选择线路模板 + 合同/价格 + 多货物行 + 箱型箱量 + 收发货人 → 生成订单。

### 8.5 演示数据（贴近真实）

- 12 家货主（光伏、汽车零部件、家电、化工、食品、钢材、医药、电子、纺织、机械、建材、快消），企业名称/信用代码/地区真实感。
- 20 家伙伴：公路 6、铁路 2、水运 3、港口/货场/堆场 6、货代 2、金融/保险 2、监管 1。
- 8 条线路模板（覆盖公铁水/铁水/公铁）、15 个港站节点、15 个货物品类、40 条价格规则、8 份合同、12 份报价、20 票订单及履约链。
- 所有编码按 6.1/6.2 规则生成；金额/时效符合行业区间。

### 8.6 验收标准

- `npm run setup` 冷启动成功（含 v1 schema 与 seed）。
- `npm run build` 零错误。
- `npm run accept`：覆盖登录（≥6 角色）、主数据、询价→报价→合同签署→下单、调度、履约、签收、账单、审计/集成消息；≥50 断言。
- `npm run e2e`：UI 全流程 + 截图（新增页面）；无 JS 异常。
- v0 演示路径与 10 个接口不回退。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 平台能力清单过大导致演示失焦 | 严格按阶段竖切，每阶段只做闭环必需能力；非目标不实现 |
| Mock 数据不像真实业务 | 编码/报文/金额/时效按标准生成；seed 固定、可复现；文档记录参数来源与假设 |
| 多角色页面膨胀 | 单 Web 端 + 角色化菜单；共用组件；每角色只给 1~2 个主工作台 |
| 与 v0 演示回归冲突 | 保持 v0 接口与路径；accept/e2e 双版本断言；每阶段回归 |
| 数据库表快速增长 | 分域命名（master_/biz_/fin_/int_ 前缀可选用）；每阶段迁移脚本可重放 |
| 文档与实现脱节 | 阶段完成必须同步 5 份文档；接口契约先于实现 |

## 附录 A：状态机（Stage 1 实现口径）

```
报价：DRAFT（询价/草稿） → SENT（已报价） → ACCEPTED（已接受，生成订单）
      / EXPIRED（过期） / CANCELLED（取消）

订单：CREATED（快速下单/待调度）
      / CONTRACTED（报价转单+已签合同） / CONFIRMED（报价转单/已确认）
      → DISPATCHED（已调度） → IN_TRANSIT（运输中） → ARRIVED（已到达）
      → SIGNED（已签收） → BILLED（已出账）
      异常分支：CANCELLED（下单后未调度前可取消）

运单：PENDING → IN_TRANSIT → ARRIVED → SIGNED
分段：PENDING → ACCEPTED → IN_TRANSIT → ARRIVED → COMPLETED
合同：DRAFT → PENDING_SIGN → SIGNED → TERMINATED
账单：ISSUED → PAID（Stage 4 启用支付）
```
