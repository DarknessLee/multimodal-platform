## 1. 核心业务流程闭环核验

对照架构方案 §2.2/§2.3 的业务流程：
`货主委托 → 报价/方案 → 合同签订 → 放箱/提箱 → 短驳运输 → 铁路/水运干线 → 港站中转 → 末端配送 → 签收回单 → 结算对账`

| 环节 | 代码/数据证据 | 状态 | 说明 |
|---|---|---|---|
| 1. 委托下单 | `orders`、`order_cargo`；`orderV1` 快速下单/订单详情 | ✅ 完整 | 支持多货物行、箱型箱量 |
| 2. 报价/方案 | `quote`/`quote_item`、`price_rule`、`platform/priceEngine` | ✅ 完整 | 分段计价、合同价/协议价/公开价优先级 |
| 3. 合同/签署 | `contract`、`e_seal`、Mock CA 报文 | ✅ 基本完整 | 合同 + 签章存证；CA 为 Mock |
| 4. 智能调度 | `dispatch_plan`/`dispatch_plan_item`/`transfer_window`、`route_template.modes` | ⚠️ 基本完整 | 支持 ROAD/SEA/RAIL 组合；快速下单默认取第一条线路（公铁水），未暴露组合选择 |
| 5. 放箱/提箱 | `container`、`container_movement`、放箱/动态/还箱 API | ⚠️ 基本完整 | 功能存在，但与公路发车无强状态约束（可先发车后放箱） |
| 6. 短驳/干线/港站中转 | `waybill_segment`（ROAD/SEA/RAIL）、分段动作、CODECO/COARRI、95306 报文 | ✅ 完整 | 公铁水三段状态推进、港站进出场/到发 |
| 7. **末端配送** | — | ❌ **缺失** | 铁路/水运到达后直接进入签收，没有“到站/到港 → 收货人门点”的末端公路分段 |
| 8. 签收回单 | `/waybills/:id/sign`、POD 上传、OCR、事件与存证 | ✅ 完整 | 签收单、回单 OCR、轨迹与存证联动 |
| 9. 计费/出账 | `POST /orders/:id/settle`、`bill`、`bill_item` | ✅ 完整 | 应收 + 各段应付 + 税额/毛利，明细和=总额 |
| 10. 对账/发票/支付/保理 | `reconciliation`、`invoice`、`payment`、`factoring_application` | ✅ 完整 | 状态机闭环；对账为手工创建/确认，无自动匹配引擎 |
| 11. 监控/预警/IoT | `monitor`、`alert`、`iot_reading`、`geo_fence` | ⚠️ 基本完整 | 温湿度/开门/停留告警可用；GPS 读数未并入 `track_point`，电子围栏仅展示不自动判定 |
| 12. 监管/运营 | `regulator_report`、`compliance_check`、`ops_*` | ⚠️ 演示级 | 报送/合规/配置/任务/健康检查完整可演示，但均为 Mock 回执 |

**闭环结论**：`下单→报价→合同→调度→运输→签收→结算→对账→发票→支付/保理` 已闭环；
**“门到门”最后一公里（末端配送）缺失**，是当前与架构业务场景最主要的差距。

## 4. 数据架构、安全与非功能对照

### 4.1 数据域与分层

- 架构 §5.2 的 7 个数据域（订单/运单/资源/货物/结算/轨迹/客户）**均有表覆盖**。
- 架构 §5.1 的 ODS/DWD/DWS/ADS 分层：**仅 `stat_daily` 模拟 ADS**，无 ODS/DWD/DWS、无标签画像。
- 主数据管理（MDM）：✅ 客户/伙伴/港站/线路/货物/箱型/价格规则统一编码。
- 数据治理/质量：⚠️ 有合规检查（箱号/单证/发票/财务/报文），但无通用数据质量平台、无脱敏/分级。

### 4.2 安全（架构 §8）

| 要求 | 实现 | 状态 |
|---|---|---|
| OAuth2/JWT 统一鉴权 | JWT + RBAC | ⚠️ 仅 JWT，无 OAuth2 授权服务器 |
| 接口限流 / SQL 注入防护 | 参数化 SQL；无速率限制 | ⚠️ 部分 |
| HTTPS/TLS、存储加密、脱敏 | 本地 HTTP；无加密/脱敏 | ❌ |
| 多因素认证/CA | Mock CA 签章 | ⚠️ Mock |
| 操作审计 | `audit_log` 全覆盖写操作 | ✅ |
| 区块链安全/国密 | 本地 SHA-256 哈希链 | ❌ 演示替代 |

### 4.3 非功能与部署（架构 §9/§10）

- K8s/多副本/HA/负载均衡/主从：❌ 未实现（本机单进程）。
- 性能指标（P99<500ms、1000 TPS、5000 轨迹点/s、500 大屏并发）：❌ 未做压测/容量验证。
- 可观测性（ELK/Prometheus/SkyWalking）：⚠️ 仅 `job_log`/`audit_log`/`ops/health` 轻量健康检查。
- 技术栈：架构选择 Java/Spring Cloud、PostgreSQL/PostGIS、Redis、TDengine、MongoDB、Kafka、ES、Flink/Doris、FISCO/长安链、EMQX、K8s；**最终实现为 Node/Express + MySQL + 本地 Mock**。这属于演示版的有意取舍，不应视为遗漏，但需在汇报时明确“非生产架构”。

## 5. 遗漏清单（按优先级）

### P0：影响核心闭环/演示结论

1. **末端配送缺失**：铁路/水运到达站/港后直接签收，无“到站/到港 → 收货人门点”的末端公路段；与架构“门到门”“末端配送”不一致。
   - 建议：签发运单时按线路终点增加末端 ROAD 段（或“客户自提”节点），签收前完成末端到达。
2. **快速下单未暴露联运组合选择**：`route_template.modes` 已支持公铁水/铁水/公铁，但快速下单未选线路时回退到第一条线路（ROAD+SEA+RAIL），演示中无法直接选择“公铁”“铁水”。
   - 建议：下单/报价页增加线路与联运组合选择，或在演示脚本中用报价路径展示三种组合。
3. **放箱/提箱与发车无强约束**：可在未放箱状态下推进公路段 ACCEPT/DEPART。
   - 建议：分段状态机增加“箱已放行”前置校验，或至少在演示中按顺序操作并在文档标注。

### P1：影响架构贴合度/可推广性

4. **电子提单（B/L）与物权凭证**：仅一单制电子运单，无独立提单、无物权转让/背书；保理基于账单而非运单物权。
5. **外部系统覆盖不足**：适配器 6 个，缺海关/口岸、公路货运平台、国家物流平台、货主 ERP/WMS、独立电子合同平台；与“≥10 个外部系统”目标有差距。
6. **GPS/IoT 与轨迹未融合**：`iot_reading` 的 GPS 点未写 `track_point`；电子围栏仅展示无自动偏航告警；轨迹更新频率与实时推送未实现。
7. **数据中台分层缺失**：只有 ADS 级 `stat_daily`，无 ODS/DWD/DWS；无标签/画像/通用数据质量。
8. **批量导入与 ERP 对接**：无 Excel 导入、无货主 ERP/WMS REST/Webhook。
9. **智能配载/路径算法/GIS 甘特**：确定性规则 + 表格看板，未实现装载优化、Dijkstra/遗传算法、GIS/甘特。
10. **对账自动匹配**：对账单手工创建/确认，无自动账单-运单匹配与差异率控制。
11. **箱损拍照 OCR / 箱区规划 / 翻倒优化**：仅维修费与简单堆存。
12. **阶梯价/回程价/复杂计费**：价格引擎规则类型有限。
13. **安全项**：无限流、TLS、存储加密、脱敏、MFA。

### P2：平台化/生产化能力

14. 微服务拆分、API 网关、独立消息/文件服务、Kafka/ES/Redis/时序库。
15. 真实联盟链（FISCO/长安链）与国密、真实 CA、真实电子合同。
16. K8s/多副本/HA/性能压测/可观测性（ELK/Prometheus/SkyWalking）。
17. 多租户、工作流引擎、移动端（货主 APP/司机端/港站作业端）。
18. 保险理赔、危险品完整校验、海关/口岸业务。

## 6. 过度开发/范围偏差审查

### 6.1 是否有“与架构无关”的模块？

**未发现完全无关的模块**。逐项映射：

| 实现 | 架构对应 | 判断 |
|---|---|---|
| 调度方案/运力池/监控/预警/IoT | §4.2/§4.5 | 对齐 |
| 单证/存证/电子印章 | §4.3 | 对齐（简化实现） |
| 财务对账/发票/支付/保理/保险 | §4.6 + §6.1 金融保险 | 对齐（第三期能力提前实现） |
| 监管报送/合规检查 | §6.1 国家物流平台/监管上报 | 对齐（Mock） |
| 运营配置/字典/任务/健康/全链路验收 | §3.1 运营管理后台 + 数据质量 | 对齐，但更偏“演示支撑” |
| 12 角色（含独立结算/运营） | §2.1 参与角色 + 运营后台 | 轻微超出（角色更细），不算过度 |

### 6.2 “广度过度、深度不足”的模块

- **保险**：有保单/保费/状态，无理赔流程。
- **监管/合规**：有报送状态机/5 类规则，无真实国家平台报送、无监管字段级标准校验。
- **运营后台**：配置/字典/任务/健康齐全，但任务为手动 Mock、无真实调度器。
- **电子围栏**：可管理/展示，无自动围栏判定。
- **区块链**：本地哈希链，无联盟链/国密/智能合约。
- **数据中台**：仅 ADS 汇总，非完整分层。

这些模块**不是过度开发**（均在架构范围内），但应标注“演示级”，避免对外宣称已生产就绪；若继续投入，应优先补深度而非继续加模块。

### 6.3 相对原始 v0 约束的规模膨胀

原始 v0 演示版要求 ≤7 表、≤10 接口、≤3 条启动命令；当前为 **59 表 / 139 路由 / 2 条启动命令**。
这是“从 v0 演进为平台化演示”的预期结果（用户明确要求按架构方案演进），**不属于跑偏**；但需要在 README/汇报中明确：
- 当前是“平台化 Mock 演示”，不是轻量 MVP；
- 表/接口数量增长来自 Stage1~5 的平台能力，而非无意义堆砌。

## 7. 结论与建议

### 7.1 总体结论

- **核心业务闭环**：`下单→报价→合同→调度→公铁水运输→签收→计费→对账→发票→支付/保理` 已闭环，可完整演示；**唯一 P0 业务断点是末端配送**，另有快速下单组合选择、放箱强约束两个演示/一致性问题。
- **架构贴合度**：业务应用层（六中心）、业务中台关键能力（规则/计费/签章/权限）与数据域覆盖较好；技术中台、数据中台、集成层、安全与非功能按“单机 Mock 演示”有意简化，与架构目标存在明显差距，但方向一致。
- **遗漏 vs 过度**：未发现无关模块；主要问题是外部集成（≥10 系统）、电子提单/联盟链、IoT 与轨迹融合、数据中台分层等“深度不足”，以及末端配送这一核心业务缺口。
- **定位建议**：可作为“业务闭环演示 + 平台化架构样例”交付；**不应宣称已满足架构方案的全部生产指标**（性能、高可用、真实链/CA/银行/税务/海关、等保等）。

### 7.2 建议的下一步（按投入产出排序）

1. **P0（演示前）**：补末端配送分段/自提节点；快速下单增加线路/联运组合选择；放箱状态前置校验；用演示脚本覆盖公铁、铁水、公铁水三种组合。
2. **P1（对外汇报前）**：明确标注 Mock/演示边界；补电子提单与多方签章说明；至少增加 2~3 个外部适配器（公路货运平台、国家物流平台/监管、货主 ERP/Webhook）作为“可扩展样例”；把 GPS 读数并入轨迹并启用围栏告警。
3. **P2（生产化）**：按架构方案补数据中台分层、消息/网关/微服务、真实联盟链/CA、K8s/HA/安全与性能验证。
4. **文档**：README/方案中区分“已实现（演示级）”“Mock/简化”“未实现”，避免读者按生产架构预期验收；本报告已同步修正 `docs/00` 的表名（`goods_catalog`/`dict_data`，补 `quote_item`/`event_outbox`）。
